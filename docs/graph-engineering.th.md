## 1. นิยามในประโยคเดียว

**Graph Engineering** = การออกแบบระบบ AI Agent ให้อยู่ในรูป **กราฟงานที่วาดไว้ล่วงหน้า** — แต่ละ **โหนด (node)** คือหนึ่งขั้นตอน แล้ว **เส้นเชื่อม (edge)** กำหนดว่างานเดินจากไหนไปไหน

Google เปรียบกับ **ผังองค์กร**: แต่ละกล่องคือคนหรือหน่วยงานที่ทำหน้าที่หนึ่ง ส่วนเส้นบอกว่างานส่งต่อให้ใคร

### โหนดสองชนิด

| ชนิด | ทำอะไร | ใช้โมเดลไหม | ผลลัพธ์ |
|---|---|---|---|
| **Agent Node** | ให้โมเดลคิดและตัดสินใจ | ใช้ | ยืดหยุ่น แต่คาดเดาไม่ได้ 100% |
| **Function Node** | รันตรรกะ/โค้ดธรรมดา | **ไม่ใช้** | กำหนดผลได้แน่นอน (deterministic) |

หลักคิด: งานไหนเขียนเป็นโค้ดได้ ให้เป็น Function Node — ถูกกว่า เร็วกว่า และไม่มีวันกุข้อมูล ใช้ Agent Node เฉพาะส่วนที่ต้องใช้วิจารณญาณจริง ๆ

## 2. สามคำที่คนสับสนที่สุด: Harness, Loop, Graph

เรียงจากชั้นในสุดไปชั้นนอกสุด:

```
┌──────────────────── Graph ────────────────────┐
│  กำหนดว่างานเดินผ่านโหนดไหน เรียงลำดับอย่างไร   │
│   ┌─────────── Harness (ต่อหนึ่ง agent) ──────┐ │
│   │ เครื่องมือ · หน่วยความจำ · guardrails      │ │
│   │   ┌──────── Loop ────────┐                │ │
│   │   │ คิด → ทำ → สังเกต → วนใหม่ │             │ │
│   │   └──────────────────────┘                │ │
│   └───────────────────────────────────────────┘ │
└────────────────────────────────────────────────┘
```

- **Harness (ชุดโครงรอบโมเดล):** ทุกอย่างที่ห่อหุ้มโมเดล — เครื่องมือที่เรียกใช้ได้ หน่วยความจำ รั้วกันความเสี่ยง (guardrails)
- **Loop (วงรอบการทำงาน):** รอบที่ agent วิ่งอยู่ในโครงนั้น — คิด ตัดสินใจ ใช้เครื่องมือ แล้ววนกลับไปคิดใหม่ จนบรรลุเป้าหมาย
- **Graph:** ชั้นที่อยู่ **เหนือขึ้นไป** กำหนดว่างานจะผ่านโหนดไหนบ้าง และเรียงลำดับอย่างไร

### Shared State — สิ่งที่ทำให้กราฟเดินได้จริง
ใน Agent Development Kit (ADK) ของ Google ทุก agent และทุกโหนดในเวิร์กโฟลว์ **แชร์สถานะเดียวกัน** ข้อมูลและบริบทจึงไหลไปตามเส้นทางของกราฟเอง โดยไม่ต้องให้แต่ละโหนดไปตามหา

## 3. Loop Engineering vs Graph Engineering (ภาพบน)

**Loop Engineering** (ภาพซ้าย "The Loop") — ตามหมายเลขในภาพ:
1. `start` รับ task เข้ามา
2. **วงใน (inner reasoning loop):** agent วน `reason → act → observe`
3. ส่งผลลัพธ์ออกมาเป็นหนึ่ง **attempt**
4. ถ้า checkpoint บอกว่า **not yet** → ส่ง **feedback for the next pass** กลับไปเริ่มรอบใหม่
5. ถ้า **checkpoint: goal reached?** → **reached** → `done`

**Graph Engineering** (ภาพขวา):
`start → agent node → agent node → function node → result`
โดยมีเส้นย้อนจาก function node กลับไปที่ agent node ตัวที่สอง — แปลว่า **กราฟก็มีลูปได้** แต่ลูปนั้นถูก **วาดกำหนดไว้** ว่าวนจากไหนไปไหน ไม่ได้ปล่อยให้ agent วนอิสระ

### ต่างกันตรงไหน

| | Loop Engineering | Graph Engineering |
|---|---|---|
| โครงสร้าง | ลูปเดียว วนจนถึงเป้า | วางกราฟไว้ก่อน งานเดินตามโหนดและเส้น |
| ใครคุมลำดับ | agent เอง | วิศวกรที่วาดกราฟ |
| เหมาะกับ | งานไม่ซับซ้อน เช่น สรุปหนึ่งย่อหน้า | งานหลายชิ้นส่วน เงื่อนไขหลายชั้น เช่น เอกสาร 50 หน้าที่มีกราฟิกหลายแบบ |

## 4. ตัวอย่าง: ระบบรีวิว Pull Request อัตโนมัติ (ภาพล่าง)

เลือกตัวอย่างนี้เพราะนักพัฒนารู้ขั้นตอนอยู่แล้ว → **รู้เวิร์กโฟลว์ล่วงหน้า = วาดกราฟได้ทันที**

```
            ┌─▶ linter ──────────────────────┐
            ├─▶ audit for dead code paths ───┤
   PR ──────┼─▶ variable naming check ───────┼─▶ join ─▶ router ─┬─ pass ─▶ human approval ✓
 (fan-out)  ├─▶ validate code comments ──────┤                    └─ fail ─▶ fixer agent
            └─▶ passing CI build ────────────┘                                  │
   ▲                                                                            │
   └──────────────────── (แก้แล้วส่งกลับเข้ารีวิวใหม่) ────────────────────────────┘
```

สามส่วนหลัก:
1. **Fan-out (กระจายงาน):** เปิด **5 สายขนาน** พร้อมกัน (linter, หาโค้ดตาย, ตรวจชื่อตัวแปร, ตรวจคอมเมนต์, ตรวจ CI) แทนที่จะทำทีละอย่างแล้วต่อคิว
2. **Join Node (รวมผล):** **รอสายที่ช้าที่สุด** ให้เสร็จ แล้วสังเคราะห์ผลทั้งหมดเป็นก้อนเดียว
3. **Router (จัดเส้นทาง):** ตัดสินว่าไปทางไหนต่อ
   - **fail** → ส่งให้ **fixer agent** (agent เฉพาะทางที่แก้โค้ด) — เส้นประในภาพพาวนกลับไปที่ PR เพื่อรีวิวใหม่
   - **pass** → **human approval** (ให้มนุษย์อนุมัติ)

> Router เปรียบเหมือน router บนเว็บเซิร์ฟเวอร์ที่จับคู่ URL กับหน้าเว็บ ต่างกันที่ปลายทางคือ agent ย่อย ผู้เชี่ยวชาญเฉพาะทาง หรือเวิร์กโฟลว์อีกชุด

สังเกต: ปลายทางที่ "ผ่าน" คือ **มนุษย์** ไม่ใช่ให้ AI merge เอง — กราฟเปิดให้วางจุดตรวจของมนุษย์ไว้ตรงไหนก็ได้อย่างชัดเจน

## 5. Graph Engineering ≠ Knowledge Graph ≠ GraphRAG

| คำ | สนใจเรื่องอะไร |
|---|---|
| **Knowledge Graph** | **ข้อมูล** — ข้อมูลแต่ละชิ้นสัมพันธ์กันอย่างไร |
| **GraphRAG** | การดึงข้อมูลมาตอบคำถาม (RAG) โดยอาศัยโครงสร้างกราฟของข้อมูล |
| **Graph Engineering** | **พฤติกรรมของระบบ** — "อะไรเข้ามาก่อน เรียงลำดับอย่างไร แล้วเกิดอะไรต่อ" |

จำง่าย ๆ: Knowledge Graph คือ "แผนที่ของข้อมูล" ส่วน Graph Engineering คือ "แผนผังของงาน"

## 6. Graph vs Agent Swarm — ใครเป็นคนกำหนดเส้นทาง

| | Graph Engineering | Agent Swarm |
|---|---|---|
| ผู้กำหนดเส้นทาง | **วิศวกร** นิยามทุกโหนด ข้อมูลหน้าตาอย่างไร เกิดอะไรในแต่ละขั้น | **ไม่กำหนดล่วงหน้า** แต่ละ agent ได้แค่บุคลิกของตัวเอง แล้วช่วยกันแก้ |
| agent ต้องรู้ประวัติก่อนหน้าไหม | ไม่จำเป็น | — |
| จุดแข็ง | คาดเดาได้ ไล่หาจุดผิดได้ ควบคุมได้ | ยืดหยุ่น |
| เหมาะกับ | ปัญหาที่ขอบเขตชัด (เช่น รีวิวโค้ด) | โจทย์คลุมเครือ |

> **รู้ขั้นตอนอยู่แล้ว → ใช้กราฟ / ยังไม่รู้ว่าคำตอบจะมาจากทางไหน → ใช้ Swarm**

## 7. Codelab: Marathon Race Day Coach

- แอปให้คำแนะนำกลยุทธ์การวิ่งและการคุมจังหวะ (pacing) ในวันแข่งมาราธอน

  4. กระจายงานแบบขนาน + โหนดรวมผล
  5. … จนถึงเวิร์กโฟลว์ที่ **รูปร่างเปลี่ยนตามอินพุต** และ **เรียกตัวเองซ้ำได้**

## 8. เลือกรูปแบบไหน — คำถามเดียวที่ต้องถาม

> **"วาดเวิร์กโฟลว์ออกมาได้ไหม ก่อนที่อินพุตจะเข้ามา?"**

| คำตอบ | รูปแบบ | ใครตัดสินเส้นทาง |
|---|---|---|
| วาดได้ | **Graph Workflow** | วิศวกร (ตอนออกแบบ) |
| รู้ว่ามีทีมไหนบ้าง แต่แต่ละคำขอใช้ทีมไม่เหมือนกัน | **Collaborative Agents** | **โมเดล** ตัดสินว่าจะเรียกใครต่อ |
| รูปร่างงานขึ้นกับอินพุตจริง ๆ | **Dynamic Workflows** | **โค้ด** ตัดสินตอนรันไทม์ |

ทั้งสามแบบ **ประกอบร่วมกันได้** — เช่น โหนดหนึ่งในกราฟข้างในบรรจุตัวประสานงานแบบ Collaborative ไว้

### ข้อสรุปของบทความ
Graph Engineering คือการนำหลัก **ควบคุมลำดับการทำงาน (control flow)** ที่วิศวกรซอฟต์แวร์ใช้กันมานาน กลับมาใช้กับ AI — คนในคลิปถึงกับแซวว่านี่คือการประดิษฐ์ Data Structures & Algorithms ใหม่สำหรับยุค agent และเทรนด์ถัดไปอาจเป็น "Hashtable Engineering" หรือ "Stack Engineering"

## 9. เชื่อมโยงกับบันทึก Harness (การวิเคราะห์ของผู้เขียนบันทึก)

บันทึก [Harness สำหรับ Agent ที่ทำงานยาว](./long-running-agent-harness.th.md) กับ Graph Engineering ไม่ได้ขัดกัน แต่อยู่ **คนละชั้น** และเสริมกัน:

| | Harness (Anthropic) | Graph Engineering (Google) |
|---|---|---|
| ปัญหาหลัก | ความจำหายข้าม **เวลา** (session ต่อ session) | ความซับซ้อนของ **ลำดับขั้น** ภายในงาน |
| เครื่องมือหลัก | บันทึกบนดิสก์: feature list, progress log, git | Shared State ส่งต่อตามเส้นกราฟ |
| ทางแก้ร่วม | **ใช้โครงสร้าง ไม่ใช่พรอมต์ที่ดีขึ้น** | **ใช้โครงสร้าง ไม่ใช่พรอมต์ก้อนใหญ่** |

หกขั้นของ coding session ในบันทึก Harness วาดเป็นกราฟได้พอดี:

```
start ─▶ [F] อ่าน progress + git log ─▶ [F] init.sh + smoke test ─▶ router
                                                                ├─ broken ─▶ [A] แก้ให้ใช้ได้ ─┐
                                                                └─ ok ◀───────────────────────┘
      ─▶ [F] เลือก feature false ตัวแรก ─▶ [A] ลงมือทำ ─▶ [F/A] e2e ในเบราว์เซอร์ ─▶ router
                                                                ├─ fail ─▶ [A] แก้ ─▶ (กลับไปทดสอบ)
                                                                └─ pass ─▶ [F] passes:true + commit + log ─▶ end
[F] = Function Node   [A] = Agent Node
```

บทเรียน: ขั้นที่ **ไม่ต้องคิด** (อ่านไฟล์, รันสคริปต์, เลือก feature จากลำดับ, commit) ควรเป็นโค้ด — เหลือให้โมเดลทำเฉพาะส่วนที่ต้องคิดจริง ซึ่งลดทั้งต้นทุนและโอกาสที่ agent จะทำผิดกติกา (เช่น แก้ test ให้ผ่าน)
